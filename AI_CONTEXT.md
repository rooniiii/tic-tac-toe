# AI CONTEXT – NEON XO game app (`tic-tac-toe`)

This file is written for AI assistants (and new developers). It describes the
whole project: purpose, architecture, data model, security model, every
important file, conventions, known limits and pitfalls. Read it fully before
changing code. A sister file with the same name exists in the admin project
(`tic-tac-toe-admin/AI_CONTEXT.md`).

---------------------------------------------------------------------------
## 1. What this is
---------------------------------------------------------------------------

- A neon-styled **tic-tac-toe game for Android**, built with **Flutter** and
  **Firebase**. University semester project.
- Package / Dart name: `tic_tac_toe`. App label on the phone: "Neon XO Game".
  Android applicationId: `com.example.tic_tac_toe`.
- A separate Flutter app, **NEON XO Admin** (folder `tic-tac-toe-admin`,
  package `neon_xo_admin`), manages players and admins. **Both apps use the
  same Firebase project `tic-tac-toe-4ab92`** and the same Firestore database.
- Firebase plan: **free Spark plan**. This is the most important constraint:
  no Cloud Functions, no Admin SDK, no server code. Everything runs in the
  client apps, and **Firestore security rules are the only server-side
  enforcement**.

## 4. App flow (screens)
---------------------------------------------------------------------------

1. `main()` → `Firebase.initializeApp` → `FirebaseAppCheck.activate(
   androidProvider: AndroidProvider.debug)` → `MobileAds.initialize()` →
   `MyApp`.
2. `MyApp` (StatefulWidget) owns a global `appNavigatorKey` and listens to
   `AccountStatusService.instance.onBlocked`. When it fires it shows a
   non-dismissible "Account Unavailable" dialog and then
   `pushAndRemoveUntil(LoginScreen)`.
3. `SplashScreen` → `AuthService.restoreSession()` → `MenuScreen(user)` if a
   session exists, else `LoginScreen`. Uses `pushReplacement`, so the menu is
   the root route (system back on the menu closes the app).
4. `LoginScreen` → `AuthService.loginWithFirebase(email, password)` →
   `pushReplacement(MenuScreen)`. "Forgot password" →
   `sendPasswordResetEmail`. Link to `SignupScreen`.
5. `SignupScreen` → `signUpWithFirebase(name, email, phone, password)`.
   Creates the Firebase login + `users/{uid}` doc, sends a verification email,
   then signs out. The player must verify the email before logging in.
6. `MenuScreen`: top bar = Logout button (with confirmation), Leaderboard
   icon, Settings icon. (A "back to login" arrow was removed on purpose.)
   Body: profile card (name, masked phone id, bio with edit dialog), stats
   row (Played / Wins / Losses / Best), difficulty selector, PLAY, How to
   play, FAQ. Settings dialog: sound effects, voice assistant, and
   **Delete my account** (password re-entry dialog `_DeleteAccountDialog`).
7. `ModeScreen`: VS COMPUTER → `GameScreen(level: 1)`; VS FRIEND →
   `JoinScreen` (guest name, no login) → `GameScreen`.
8. `GameScreen`: board, undo (2 per game, +1 per player via rewarded ad),
   hints (3), voice announcements. At the end it saves locally (SQLite) and
   calls `FirestoreSyncService().syncGameResult(...)` with `unawaited` (errors
   only logged). Win vs computer → `WinScreen` (score += 10 × level, "next
   level" pushes GameScreen with level + 1). Draw → dialog. Loss → dialog.
9. `LeaderboardScreen`: `DefaultTabController` with two tabs – local
   performance (from SQLite) and Global Top 20 (Firestore `leaderboard`,
   highlights the current player).

Navigation is plain `Navigator.push / pushReplacement / pushAndRemoveUntil`
with `MaterialPageRoute`. No named routes, no router package.

## 5. Game logic and AI
---------------------------------------------------------------------------

- `GameLogic`: board `List<Mark?>` of 9 cells (index 0–8, row-major),
  move history for undo, `play(i)`, `undo()`, `reset()`, `winner`,
  `winLine`, `isDraw`, `isOver`. Static `winLineOf(board)` / `winnerOf(board)`
  are reused by the AI. X always starts.
- `Player` (abstract) → `HumanPlayer` (waits for taps, `chooseMove` returns
  null) and `ComputerPlayer` (abstract, factory
  `ComputerPlayer.forDifficulty`):
  - `EasyComputer`: random empty cell.
  - `MediumComputer`: 25% random; otherwise win if possible, else block,
    else take centre, else random.
  - `HardComputer`: full **minimax** (score 10 − depth / depth − 10, random
    tie-break among best moves). Unbeatable.
- The design is intentionally OOP (inheritance, polymorphism, encapsulation
  with private fields + getters) – useful for the course report.

## 6. Authentication and sessions (logic/auth_service.dart)
---------------------------------------------------------------------------

Public API (screens depend on it – keep it stable):
`loginWithFirebase`, `signUpWithFirebase`, `sendPasswordResetEmail`,
`restoreSession`, `logout`, `deleteOwnAccount`, `handleBlockedAccount`,
`blockedMessage` (static const), plus legacy local-only methods `signUp`,
`login`, `secureLogin`, `getPlayers`, `deleteUser`, `ensureAdminExists`.
`LoginResult` = `{User? user, String? error}`.

Login (`loginWithFirebase`):
1. `LoginAttemptLimiter.checkLock(email)` – escalating lock after 3 wrong
   passwords (10 s, 60 s, 2 min, 5 min, 10 min, 30 min, 1 h).
2. Firebase `signInWithEmailAndPassword` (20 s timeout), `reload()`.
3. Read `users/{uid}`. If missing → fail "User profile not found".
4. If `isBlocked == true` or `status == 'blocked'` →
   `handleBlockedAccount` (marks blocked on device, removes offline login,
   signs out) → fail with `blockedMessage`.
5. If `emailVerificationRequired` and not verified → resend verification,
   sign out, fail.
6. Save offline credentials (PBKDF2 hash in SQLite + email→phone link in
   prefs), clear attempts, save active session email, then
   `_onOnlineSessionStarted()` = start the live block listener + sync the
   leaderboard entry.
7. Network errors / timeouts → **offline login** via
   `OfflineCredentialsStore.login` (only works after one successful online
   login on that device, refused if the device has the blocked flag).

`restoreSession` (app start): if Firebase still has a user → reload, read
profile, same blocked/verification checks, start listener. On timeout or
temporary Firebase error → `_restoreLocalSession` (offline), which also
refuses blocked accounts and starts the listener if a Firebase user exists.

`deleteOwnAccount(password, phone)`: re-authenticates with
`EmailAuthProvider.credential`, stops the listener, deletes the player's
`game_history` docs (pages of 400), then `leaderboard`, `user_profiles`,
`player_stats`, `users` docs in one batch, then `user.delete()` (removes the
Firebase login), then local SQLite user + prefs.

Local identity: the SQLite `AppUsers` table is keyed by **phone number**.
`User` objects passed between screens hold name, phone, passwordHash, salt.
Firestore identity is the Firebase **UID**. The link between them is the
`phone` field in `users/{uid}`.

Password hashing (`auth/password_hasher.dart`): device-stored passwords use
`pbkdf2-sha256$10000$<base64>` with a random 16-byte salt. `verify()` also
accepts the legacy format (hex `sha256(salt + password)`), and
`needsUpgrade()` triggers a re-hash on the next successful login. Firebase
Auth itself stores the real online password; the device hash exists only
for offline login and local two-player accounts.

## 7. Blocking / deletion detection (services/account_status_service.dart)
---------------------------------------------------------------------------

Singleton `AccountStatusService.instance`:
- `startWatching()` – Firestore `snapshots()` listener on the current
  player's `users/{uid}`. If the doc becomes blocked → `_reportBlocked`.
  If the doc disappears (server-confirmed, not cache) → reported with
  `removedMessage` ("removed by an administrator").
- `_reportBlocked` → `AuthService().handleBlockedAccount(email)` → emits on
  the broadcast stream `onBlocked` → `main.dart` shows the dialog and goes to
  the login screen.
- `ensureActive()` – one-off check before writes (used by
  `FirestoreSyncService` and `ProfileService._syncBio`); throws
  `AccountBlockedException`. Skips silently when offline.
- `checkAfterFailure(error)` – after a `permission-denied` write error,
  re-checks the status.
- `stopWatching()` – called from `logout()`.

## 8. Firestore data model (shared with the admin app)
---------------------------------------------------------------------------

| Collection | Doc id | Fields | Written by |
|---|---|---|---|
| `users` | uid | uid, name, email (lowercase), phone, emailVerificationRequired (true), createdAt, emailVerifiedAt, updatedAt; admin-only: isBlocked, status ('active'/'blocked'), blockedAt, blockedBy | game sign-up; admin |
| `player_stats` | uid | uid, email, gamesPlayed, wins, losses, draws, updatedAt (FieldValue.increment) | game |
| `game_history` | auto | player1Uid, player1Email, opponentType ('computer'/'guest'/'player'), opponentName, difficulty (nullable), resultForPlayer1 ('win'/'loss'/'draw'), completedAt (server time) | game |
| `user_profiles` | uid | uid, phone, bio (≤ 40 chars), updatedAt | game; admin edits/deletes bio |
| `leaderboard` | uid | uid, name, gamesPlayed, wins, losses, draws, updatedAt – public copy without email | game (transaction) ; admin rename/delete |
| `admins` | uid | role ('admin'), name, email, createdAt, createdBy | admin app only |
| `admin_logs` | auto | action, adminUid, adminEmail, targetUid, targetName, details, createdAt | admin app only |
| `deleted_users` | uid | email, deletedAt, deletedBy – tombstone so a deleted player cannot recreate a profile | admin app only |

Writes from the game per finished online game (`syncGameResult`):
`ensureActive()` → batch { set `game_history/{auto}`, merge-set
`player_stats/{uid}` with increments } → `LeaderboardService().syncMyEntry()`
(transaction: read `player_stats` + `users`, write `leaderboard/{uid}`).
Offline: Firestore's local cache queues the batch until online.

Local SQLite (Drift, schemaVersion 1): `AppUsers` (id, name, phone unique,
passwordHash, salt, createdAt), `GameHistory` (local history incl.
player2UserId, movesJson), `PlayerOpponentStats` (per user / opponentType /
difficulty counters), `UserProfiles` (userId PK, bio, avatarPath,
updatedAt). SharedPreferences keys: `active_session_email`,
`offline_phone_<email>`, `account_blocked_<email>`,
`login_fails_/login_lock_until_/login_lock_level_<email>`,
`pending_bio_<phone>`, `best_<phone>`, `best2p_<phone>`, `music`, `sound`,
`voiceAssistant`, `sqlite_users_migrated`, legacy `users`.

## 9. Security rules (firestore.rules) – summary
---------------------------------------------------------------------------

The file lives ONLY in this repo but protects both apps. Deploy from this
folder: `firebase deploy --only firestore:rules` (or paste in console).

Helpers: `isAdmin()` (admins/{uid}.role == 'admin'), `isOwner(uid)`,
`isBlocked()`, `activePlayer()` = signed in AND own `users` doc exists AND
not blocked, `validEmail(v)` = string ≤ 254 chars,
`adminOnlyUserFields()` = isBlocked, status, blockedAt, blockedBy, uid,
email, emailVerificationRequired.

- `admins`: read own or admin; create/update admin only (email ≤ 254);
  delete admin.
- `deleted_users`: admin only. `admin_logs`: admin read; admin create with
  adminUid == auth.uid and createdAt == request.time; never update/delete.
- `users`: read own/admin; create own only if no tombstone, not blocked,
  emailVerificationRequired true, email ≤ 254, no block fields; update admin,
  or owner (not blocked) without touching admin-only fields; delete admin or
  owner (active).
- `player_stats`: read own/admin; create = exactly 1 game; update =
  gamesPlayed +1 and exactly one of wins/losses/draws +1; allowed keys
  fixed; delete admin or owner.
- `game_history`: read admin or own; create by active player for self with
  valid result and fixed keys; no update; delete admin or own.
- `user_profiles`: read own/admin; write admin or active owner (bio ≤ 40,
  fixed keys); delete admin or owner.
- `leaderboard`: read any signed-in user; owner create/update only if every
  number equals their real `player_stats` and name equals `users.name`;
  admin update/delete; owner delete.
- Everything else denied.

## 10. Free-plan limitation and the workaround (important design decision)
---------------------------------------------------------------------------

Disabling/deleting a Firebase **login** for another user requires the Admin
SDK (server) → paid Blaze plan. Instead:
1. Admin app sets `isBlocked` on `users/{uid}`.
2. Rules reject every write from a blocked player and stop players from
   editing block fields.
3. The game watches the profile, signs the player out immediately, refuses
   login (online and offline) and wipes the offline login on the device.
Deleted players: data deleted + `deleted_users` tombstone; the game signs
them out (profile gone); the orphan Firebase login stays (removable by hand
in the console). Self-deletion from the game DOES remove the login.

Admins are created from the admin app via a **second FirebaseApp instance**
(so the current admin is not signed out) – see the admin AI_CONTEXT.

## 11. Conventions for changes
---------------------------------------------------------------------------

- Colours: use `AppTheme` constants (background #0B0B2B, purple #7B2FF7,
  neonCyan #00E5FF, neonPink #FF2BD6, neonYellow #FFD600). Dark neon style.
- Text inputs: use `NeonTextField`. Limits: name 3–40 letters only,
  password 8–40 chars with upper, lower, digit and special character
  (`Validators.password` + `PasswordChecklist`), **email max
  254 (`Validators.maxEmailLength`) with a visible counter**
  (`showCounter: true`, helperText "Maximum 254 characters").
- Accessibility: buttons call `AudioService.playButtonSound()` and
  `_announce(label)` for the voice assistant – keep that pattern in new UI.
- Debug output: wrap logs in `if (kDebugMode)`; auth timing logs already do.
- Firestore: always handle offline (timeouts, cached reads), never block
  gameplay on network writes (`unawaited` + catch).
- Any new collection or field written by a client MUST be added to
  `firestore.rules`, otherwise it is denied.
- Queries: Firestore needs a composite index for multi-field filters/sorts
  or multi-field aggregations. Prefer single-field queries (auto-indexed).
- Files use Windows CRLF line endings; repo is on OneDrive. Keep CRLF.
- Keep `AuthService`'s public API stable – screens depend on it.

## 12. Known limitations / technical debt
---------------------------------------------------------------------------

- Game results are computed on the device; rules limit them (one game at a
  time, valid values) but a modified client could still report fake wins.
- A blocked player who stays offline can play locally until reconnecting.
- App Check uses the debug provider (no real protection in release).
- Only Android configured; iOS/web/windows would crash at Firebase init.
- `functions/` and `functions_admin/` are empty templates; `firebase.json`
  still lists them, so never run plain `firebase deploy`.
- Tests: see `test/` (unit + widget). Still missing: Firestore rules
  tests with the emulator, and GameScreen/MenuScreen widget tests (they need
  Firebase/AdMob fakes). Earlier candidates were `GameLogic`,
  `HardComputer` (never loses), `Validators`, `PasswordHasher`, rules tests
  with the Firebase emulator.
- `User`/`AdminUser` local model and `ensureAdminExists()` are legacy from a
  pre-Firebase version (admin login used to be local); harmless.
- `menu_screen.dart` is large (~950 lines) and could be split.
- Release build signed with debug key; AdMob uses Google's test ids.

## 14. Features added 2026-11-27
---------------------------------------------------------------------------

**Level progression (`logic/level_progress_service.dart`)** – 1000 levels
per difficulty (`LevelProgressService.maxLevel`). Progress is saved in
prefs `level_<phone>_<difficulty>`; `ModeScreen` starts VS COMPUTER at the
saved level (1 for new players). `GameScreen` calls `recordWin` on a win
(never moves progress backwards). Winning level 1000 resets progress to 1,
increments `level_done_<phone>_<difficulty>`, and `WinScreen` shows the
"CHAMPION!" screen with only a RETURN TO HOME button.

**Admin-managed ads (`services/house_ad_service.dart`,
`screens/ad_countdown_screen.dart`)** – Firestore `ads` collection
(title ≤ 60, message ≤ 200, imageUrl https ≤ 500, countdownSeconds 5–60,
default 15, active). The game reads `where active == true` (cached 10 min)
and shows a full-screen ad with a countdown; CONTINUE / system back unlock
at 0. Shown (a) before every 3rd level (`shouldShowBeforeLevel`) and (b) as
the fallback reward for "+1 UNDO" when no AdMob ad is loaded (reward only
when watched fully).

**Session (`logic/auth/session_manager.dart`)** – device session "cookie":
random 256-bit token + issued/last-active time in prefs. Expires after 30
days total or 14 days idle → `restoreSession` logs out and returns
`AuthService.sessionExpiredMessage`. Old sessions without a token are
upgraded, not kicked out. Logout / account deletion clear it.

**Onboarding (`logic/onboarding_service.dart`)** – first time a player
reaches the menu on a device (`onboarding_done_<phone>`), `TutorialScreen(
firstRun: true)` is shown: the 4 how-to-play pages plus pages on levels,
gestures and the AI assistant. Replay: Settings → "Replay introduction".

**AI assistant (`services/ai_assistant_service.dart`,
`screens/ai_assistant_screen.dart`)** – Groq chat completions
(`https://api.groq.com/openai/v1/chat/completions`) via `dart:io`
HttpClient (no new package). Key/model from build defines:
`secrets.json` in the project root (git-ignored; template
`secrets.example.json`: `{"GROQ_API_KEY": "...", "GROQ_MODEL": "..."}`).
VS Code: `.vscode/launch.json` passes `--dart-define-from-file=secrets.json`
on Run/F5. Terminal: `flutter run --dart-define-from-file=secrets.json`
(same flag for `flutter build apk`).
(default model `llama-3.1-8b-instant`). Never commit the key. Limits:
local 10 req/min and 3 s gap; HTTP 429 → friendly message with the
`retry-after` wait and a visible cooldown; other errors mapped to friendly
text. Input ≤ 500 chars, last 10 messages sent. NOTE: a key inside an APK
can be extracted; for production, route calls through a server.

**Accessibility / gestures** – board cells have Semantics labels ("Row 1,
column 2, empty"); tools have Semantics; status is a live region. Game
board: swipe left = Undo, swipe right = Hint; double-tap the top bar =
speak + show status. Tutorial pages are swipeable with a page-indicator
label.

**Bottom overflow fix** – `TutorialScreen` page content was a fixed
~600 px Column inside an Expanded PageView (overflowed 73 px on 360×640).
Now a LayoutBuilder + scroll view with a height-scaled picture.
`GameScreen` computes the board size from free space and can scroll. Menu
dialogs use `scrollable: true`. Regression test:
`test/layout_overflow_test.dart`; unit tests: `test/new_features_test.dart`.

**Security** – `logic/input_sanitizer.dart` (control chars removed, hard
length limits, https-only URLs). Rules: `ads` validated (keys, types,
sizes); `admin_logs` text sizes capped. Transport is HTTPS/TLS (Firebase,
Groq); Firestore/Drift take parameters, never query strings, so SQL
injection is not possible. **Redeploy rules after this change.**

**Testability** – Firebase instances in services are `late final` (lazy),
so widgets can be built in tests without `Firebase.initializeApp`; in the
app Firebase is always initialised before first use. Keep new service
fields lazy too.
